# Requirements Document

## Введение

Сервис EasyP API выполняет генерацию protobuf/gRPC-кода через Docker-контейнеры. Текущая реализация (`Core.Generate`) вызывает Docker синхронно без контроля параллелизма — каждый gRPC-запрос порождает новый Docker-контейнер без ограничений. Это создаёт риск исчерпания ресурсов хоста при всплесках нагрузки.

Данная фича вводит in-memory worker pool — фиксированный пул горутин-воркеров, обрабатывающих запросы на генерацию через буферизированный канал. Паттерн аналогичен существующему audit worker (`internal/adapters/audit/worker.go`), но расширен до N воркеров с поддержкой backpressure, таймаутов и retry.

## Глоссарий

- **Worker_Pool** — компонент, управляющий набором горутин-воркеров, которые читают задания из буферизированного канала и выполняют генерацию кода через Docker-контейнеры.
- **Worker** — одна горутина внутри Worker_Pool, обрабатывающая задания последовательно.
- **Job** — единица работы, содержащая запрос на генерацию (`GenerateCodeRequest`) и канал для возврата результата вызывающей стороне.
- **Job_Queue** — буферизированный Go-канал, через который gRPC-обработчик отправляет Job воркерам.
- **Core** — бизнес-логика сервиса (`internal/core`), оркестрирующая генерацию кода.
- **Registry** — адаптер (`internal/adapters/registry`), предоставляющий доступ к плагинам и выполняющий Docker-контейнеры.
- **gRPC_Handler** — обработчик `GenerateCode` в API-слое (`internal/api`), принимающий запросы от клиентов.
- **Backpressure** — механизм противодавления: отклонение новых запросов при заполненной Job_Queue.
- **Generation_Timeout** — максимальное время выполнения одного задания генерации.
- **Transient_Error** — временная ошибка Docker (сбой демона, таймаут pull), при которой повторная попытка может быть успешной.

## Требования

### Требование 1: Инициализация Worker_Pool

**User Story:** Как оператор сервиса, я хочу, чтобы при старте приложения запускался пул воркеров с настраиваемым количеством горутин, чтобы контролировать параллелизм Docker-контейнеров.

#### Критерии приёмки

1. WHEN приложение запускается, THE Worker_Pool SHALL создать указанное в конфигурации количество горутин-воркеров и буферизированный Job_Queue указанной ёмкости.
2. THE Worker_Pool SHALL принимать количество воркеров и размер буфера Job_Queue как параметры конфигурации.
3. IF количество воркеров в конфигурации меньше 1, THEN THE Worker_Pool SHALL использовать значение по умолчанию, равное 1.
4. IF размер буфера Job_Queue в конфигурации меньше 0, THEN THE Worker_Pool SHALL использовать значение по умолчанию, равное 0.

### Требование 2: Отправка задания в Worker_Pool

**User Story:** Как gRPC-клиент, я хочу, чтобы мой запрос на генерацию был передан в пул воркеров и я получил результат синхронно, чтобы использовать стандартный gRPC request-response паттерн.

#### Критерии приёмки

1. WHEN gRPC_Handler получает запрос GenerateCode, THE Core SHALL создать Job с запросом и каналом ответа, отправить Job в Job_Queue и заблокироваться до получения результата из канала ответа.
2. WHEN Job успешно помещён в Job_Queue и Worker завершает обработку, THE Core SHALL вернуть результат генерации вызывающему gRPC_Handler.
3. IF Job_Queue заполнена и отправка Job невозможна без блокировки, THEN THE Core SHALL немедленно вернуть ошибку с кодом ResourceExhausted и сообщением «server overloaded».

### Требование 3: Обработка задания воркером

**User Story:** Как оператор сервиса, я хочу, чтобы каждый воркер последовательно обрабатывал задания из очереди, вызывая генерацию через Registry, чтобы ограничить количество одновременных Docker-контейнеров.

#### Критерии приёмки

1. WHILE Worker_Pool запущен, THE Worker SHALL читать Job из Job_Queue и вызывать Registry для выполнения генерации кода.
2. WHEN Worker завершает обработку Job, THE Worker SHALL отправить результат (ответ или ошибку) в канал ответа Job.
3. THE Worker SHALL обрабатывать задания строго последовательно — одно задание за раз на каждый Worker.

### Требование 4: Таймаут генерации

**User Story:** Как оператор сервиса, я хочу ограничить время выполнения каждого задания генерации, чтобы зависший Docker-контейнер не блокировал воркер навсегда.

#### Критерии приёмки

1. WHEN Worker начинает обработку Job, THE Worker SHALL создать контекст с Generation_Timeout и передать контекст в вызов Registry.
2. THE Worker_Pool SHALL принимать значение Generation_Timeout как параметр конфигурации.
3. IF Generation_Timeout истекает до завершения генерации, THEN THE Worker SHALL отменить выполнение и вернуть ошибку DeadlineExceeded в канал ответа Job.
4. IF значение Generation_Timeout в конфигурации не задано или равно 0, THEN THE Worker_Pool SHALL использовать значение по умолчанию, равное 120 секундам.

### Требование 5: Повторные попытки при транзиентных ошибках

**User Story:** Как gRPC-клиент, я хочу, чтобы воркер автоматически повторял генерацию при временных ошибках Docker, чтобы кратковременные сбои не приводили к отказу.

#### Критерии приёмки

1. IF Worker получает Transient_Error при вызове Registry, THEN THE Worker SHALL повторить вызов до настроенного максимального количества попыток.
2. THE Worker_Pool SHALL принимать максимальное количество повторных попыток как параметр конфигурации.
3. IF все повторные попытки исчерпаны, THEN THE Worker SHALL вернуть последнюю полученную ошибку в канал ответа Job.
4. IF значение максимального количества повторных попыток в конфигурации не задано или равно 0, THEN THE Worker_Pool SHALL использовать значение по умолчанию, равное 2.
5. WHILE Worker выполняет повторную попытку, THE Worker SHALL проверять контекст Job на отмену и прекращать повторы при отменённом контексте.

### Требование 6: Graceful Shutdown

**User Story:** Как оператор сервиса, я хочу, чтобы при остановке приложения Worker_Pool корректно завершал работу — дождался текущих заданий и не принимал новые, чтобы минимизировать потерю данных.

#### Критерии приёмки

1. WHEN приложение получает сигнал завершения, THE Worker_Pool SHALL прекратить приём новых Job в Job_Queue.
2. WHILE в Job_Queue остаются необработанные Job, THE Worker_Pool SHALL дождаться завершения обработки текущих заданий воркерами в пределах настроенного таймаута завершения.
3. IF таймаут завершения истекает, THEN THE Worker_Pool SHALL отменить контексты оставшихся заданий и вернуть ошибку в каналы ответа незавершённых Job.
4. WHEN все воркеры завершили работу, THE Worker_Pool SHALL залогировать количество потерянных заданий (если есть) и вернуть управление вызывающему коду.

### Требование 7: Конфигурация Worker_Pool

**User Story:** Как оператор сервиса, я хочу настраивать параметры Worker_Pool через конфигурационный файл, чтобы адаптировать поведение под ресурсы хоста.

#### Критерии приёмки

1. THE Worker_Pool SHALL поддерживать следующие параметры конфигурации: количество воркеров, размер буфера Job_Queue, Generation_Timeout, максимальное количество повторных попыток, таймаут graceful shutdown.
2. THE Worker_Pool SHALL загружать конфигурацию из секции `worker_pool` файла `config.yml` или из переменных окружения с префиксом `WORKER_POOL_`.
3. WHEN параметр конфигурации не задан, THE Worker_Pool SHALL использовать значения по умолчанию, определённые в соответствующих требованиях.

### Требование 8: Наблюдаемость Worker_Pool

**User Story:** Как оператор сервиса, я хочу видеть метрики и логи Worker_Pool, чтобы мониторить загрузку пула и диагностировать проблемы.

#### Критерии приёмки

1. WHEN Worker завершает обработку Job, THE Worker_Pool SHALL логировать результат (успех или ошибка) с идентификатором плагина и длительностью выполнения.
2. WHEN Core отклоняет Job из-за заполненной Job_Queue, THE Worker_Pool SHALL логировать событие backpressure с уровнем Warn.
3. WHEN Worker выполняет повторную попытку, THE Worker_Pool SHALL логировать номер попытки и причину повтора.
