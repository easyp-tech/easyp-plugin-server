# Документ требований: Миграция стека наблюдаемости

## Введение

Миграция стека наблюдаемости (observability) сервиса EasyP API Service с текущей конфигурации (Prometheus + Loki + Promtail + Grafana) на полный стек Grafana LGTM (Loki, Grafana, Tempo, Mimir) с добавлением Pyroscope, Alloy, RustFS и Traefik. Цель — получить единую платформу для логов, метрик, трейсов и профилирования с S3-совместимым объектным хранилищем, а также упростить локальную разработку через Traefik как reverse proxy.

## Глоссарий

- **Docker_Compose**: файл конфигурации `docker-compose.yml`, описывающий все сервисы локальной среды разработки
- **Traefik**: reverse proxy и сервис-дискавери для маршрутизации HTTP-трафика к контейнерам
- **RustFS**: S3-совместимое объектное хранилище, используемое как бэкенд для Mimir, Loki, Tempo и Pyroscope
- **Mimir**: система хранения метрик от Grafana, заменяющая Prometheus для долгосрочного хранения
- **Loki**: система агрегации логов от Grafana
- **Tempo**: система распределённого трейсинга от Grafana
- **Alloy**: унифицированный коллектор телеметрии от Grafana, заменяющий Promtail; собирает логи, метрики и трейсы
- **Pyroscope**: система непрерывного профилирования от Grafana
- **Grafana**: платформа визуализации для дашбордов, логов, метрик, трейсов и профилей
- **Init_Buckets**: сервис инициализации, создающий необходимые S3-бакеты в RustFS при запуске
- **EasyP_Service**: Go gRPC-сервис для генерации кода из protobuf-плагинов
- **Docker_Registry**: реестр Docker-образов для хранения образов плагинов
- **OTLP**: OpenTelemetry Protocol — стандартный протокол передачи телеметрии (метрики, трейсы, логи)

## Требования

### Требование 1: Reverse proxy через Traefik

**User Story:** Как разработчик, я хочу иметь единую точку входа для всех сервисов через Traefik, чтобы упростить маршрутизацию и сервис-дискавери в локальной среде.

#### Критерии приёмки

1. THE Docker_Compose SHALL включать сервис Traefik версии 3.x в качестве reverse proxy
2. WHEN Docker_Compose запускается, THE Traefik SHALL автоматически обнаруживать все сервисы через Docker provider
3. THE Docker_Compose SHALL определять Traefik-лейблы для маршрутизации HTTP-трафика к каждому сервису, имеющему веб-интерфейс (Grafana, RustFS)
4. THE Docker_Compose SHALL использовать переменные окружения с значениями по умолчанию для конфигурации портов (например, `${EASYP_TRAEFIK_PORT:-80}`)

### Требование 2: S3-совместимое объектное хранилище (RustFS)

**User Story:** Как разработчик, я хочу использовать S3-совместимое объектное хранилище для бэкендов Mimir, Loki, Tempo и Pyroscope, чтобы обеспечить надёжное и масштабируемое хранение данных наблюдаемости.

#### Критерии приёмки

1. THE Docker_Compose SHALL включать сервис RustFS как S3-совместимое объектное хранилище
2. THE RustFS SHALL предоставлять S3 API для доступа со стороны Mimir, Loki, Tempo и Pyroscope
3. WHEN Docker_Compose запускается, THE Init_Buckets SHALL создавать бакеты `mimir`, `loki`, `tempo` и `pyroscope` в RustFS
4. THE Init_Buckets SHALL завершать работу после успешного создания всех бакетов
5. IF Init_Buckets не может подключиться к RustFS, THEN THE Init_Buckets SHALL повторять попытки подключения до успешного создания бакетов

### Требование 3: Хранение метрик через Mimir

**User Story:** Как разработчик, я хочу заменить Prometheus на Mimir для хранения метрик, чтобы получить масштабируемое хранилище метрик с S3-бэкендом.

#### Критерии приёмки

1. THE Docker_Compose SHALL включать сервис Mimir вместо Prometheus
2. THE Mimir SHALL использовать RustFS в качестве бэкенда для хранения блоков метрик
3. THE Mimir SHALL принимать метрики через remote write API от Alloy
4. THE Docker_Compose SHALL монтировать конфигурационный файл Mimir из директории `./configs/mimir/`
5. WHEN Mimir запускается, THE Mimir SHALL ожидать доступности бакета `mimir` в RustFS

### Требование 4: Обновление Loki для работы с S3-бэкендом

**User Story:** Как разработчик, я хочу перевести Loki с локальной файловой системы на S3-бэкенд через RustFS, чтобы унифицировать хранение данных наблюдаемости.

#### Критерии приёмки

1. THE Docker_Compose SHALL обновить сервис Loki для использования RustFS в качестве объектного хранилища вместо локальной файловой системы
2. THE Loki SHALL хранить чанки и индексы в бакете `loki` в RustFS
3. THE Docker_Compose SHALL монтировать обновлённый конфигурационный файл Loki из директории `./configs/loki/`
4. WHEN Loki запускается, THE Loki SHALL ожидать доступности бакета `loki` в RustFS

### Требование 5: Распределённый трейсинг через Tempo

**User Story:** Как разработчик, я хочу добавить распределённый трейсинг через Tempo, чтобы отслеживать выполнение запросов через все компоненты системы.

#### Критерии приёмки

1. THE Docker_Compose SHALL включать сервис Tempo для хранения и запроса трейсов
2. THE Tempo SHALL использовать RustFS в качестве бэкенда для хранения трейсов
3. THE Tempo SHALL принимать трейсы по протоколу OTLP (gRPC и HTTP)
4. THE Docker_Compose SHALL монтировать конфигурационный файл Tempo из директории `./configs/tempo/`
5. WHEN Tempo запускается, THE Tempo SHALL ожидать доступности бакета `tempo` в RustFS

### Требование 6: Унифицированный коллектор телеметрии Alloy

**User Story:** Как разработчик, я хочу заменить Promtail на Alloy как единый коллектор телеметрии, чтобы собирать логи, метрики и трейсы через один компонент.

#### Критерии приёмки

1. THE Docker_Compose SHALL включать сервис Alloy вместо Promtail
2. THE Alloy SHALL собирать логи из Docker-контейнеров и отправлять их в Loki
3. THE Alloy SHALL скрейпить метрики с EasyP_Service (порт 8081) и отправлять их в Mimir через remote write
4. THE Alloy SHALL принимать трейсы по протоколу OTLP и пересылать их в Tempo
5. THE Docker_Compose SHALL монтировать конфигурационный файл Alloy из директории `./configs/alloy/`
6. THE Alloy SHALL иметь доступ к Docker-сокету для обнаружения контейнеров

### Требование 7: Непрерывное профилирование через Pyroscope

**User Story:** Как разработчик, я хочу добавить непрерывное профилирование через Pyroscope, чтобы анализировать производительность сервиса в реальном времени.

#### Критерии приёмки

1. THE Docker_Compose SHALL включать сервис Pyroscope для сбора и хранения профилей
2. THE Pyroscope SHALL использовать RustFS в качестве бэкенда для хранения данных профилирования
3. THE Docker_Compose SHALL монтировать конфигурационный файл Pyroscope из директории `./configs/pyroscope/`
4. WHEN Pyroscope запускается, THE Pyroscope SHALL ожидать доступности бакета `pyroscope` в RustFS

### Требование 8: Обновление Grafana с новыми источниками данных

**User Story:** Как разработчик, я хочу обновить Grafana для работы со всеми новыми источниками данных (Mimir, Loki, Tempo, Pyroscope), чтобы визуализировать метрики, логи, трейсы и профили в одном интерфейсе.

#### Критерии приёмки

1. THE Docker_Compose SHALL обновить сервис Grafana до версии 12.3.x или выше
2. THE Grafana SHALL быть сконфигурирована с источниками данных: Mimir (метрики), Loki (логи), Tempo (трейсы), Pyroscope (профили)
3. THE Grafana SHALL настроить корреляцию между источниками данных (переход из логов в трейсы, из трейсов в профили)
4. THE Docker_Compose SHALL монтировать обновлённые конфигурационные файлы Grafana из директории `./configs/grafana/`
5. THE Grafana SHALL иметь Traefik-лейблы для маршрутизации через reverse proxy

### Требование 9: Сохранение существующих сервисов

**User Story:** Как разработчик, я хочу сохранить Docker Registry и PostgreSQL в docker-compose, чтобы не нарушить работу основного функционала EasyP.

#### Критерии приёмки

1. THE Docker_Compose SHALL сохранить сервис Docker_Registry для хранения образов плагинов
2. THE Docker_Compose SHALL сохранить сервис PostgreSQL для хранения данных приложения
3. THE Docker_Compose SHALL использовать переменные окружения с значениями по умолчанию для портов Docker_Registry и PostgreSQL
4. WHEN Docker_Compose запускается, THE Docker_Registry SHALL быть доступен для загрузки и скачивания образов плагинов

### Требование 10: Адаптация EasyP_Service для нового стека

**User Story:** Как разработчик, я хочу адаптировать EasyP_Service для работы с новым стеком наблюдаемости, чтобы сервис отправлял телеметрию через OTLP.

#### Критерии приёмки

1. THE EasyP_Service SHALL продолжать экспортировать метрики в формате Prometheus на порту 8081 для скрейпинга Alloy
2. THE Docker_Compose SHALL настроить EasyP_Service с переменными окружения для подключения к Alloy по протоколу OTLP (для трейсов)
3. THE Docker_Compose SHALL определять зависимости EasyP_Service от PostgreSQL и сервисов наблюдаемости

### Требование 11: Конфигурационные файлы инфраструктуры

**User Story:** Как разработчик, я хочу иметь все конфигурационные файлы инфраструктуры в директории `./configs/`, чтобы структура проекта была единообразной и понятной.

#### Критерии приёмки

1. THE Docker_Compose SHALL монтировать все конфигурационные файлы из директории `./configs/` вместо текущей `./infrastructure/`
2. THE Docker_Compose SHALL включать конфигурационные файлы для: Traefik, Mimir, Loki, Tempo, Alloy, Pyroscope и Grafana
3. WHEN конфигурационный файл отсутствует, THE Docker_Compose SHALL завершаться с ошибкой при запуске соответствующего сервиса

### Требование 12: Переменные окружения и порты

**User Story:** Как разработчик, я хочу управлять портами сервисов через переменные окружения с значениями по умолчанию, чтобы избежать конфликтов портов в локальной среде.

#### Критерии приёмки

1. THE Docker_Compose SHALL использовать переменные окружения с префиксом `EASYP_` и значениями по умолчанию для всех внешних портов
2. THE Docker_Compose SHALL определять значения по умолчанию для портов: Traefik (80), Grafana (3000), PostgreSQL (5432), Docker_Registry (5005), gRPC (8080), метрики (8081), health (8082), gateway (8083)
3. WHEN переменная окружения не задана, THE Docker_Compose SHALL использовать значение по умолчанию для соответствующего порта
