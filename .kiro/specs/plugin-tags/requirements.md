# Документ требований: Plugin Tags

## Введение

Добавление поддержки тегов (массив строк) для каждого плагина в EasyP API Service. Теги позволяют категоризировать плагины (например, `go`, `grpc`, `gateway`, `official`, `community`) и фильтровать их при запросе списка. Изменения затрагивают все слои: схему БД, proto-определение, доменную модель, адаптер реестра, API и SDK.

## Глоссарий

- **Plugin_Tags_Service** — EasyP API Service, централизованная платформа для генерации кода protobuf/gRPC через Docker-контейнеры
- **Plugin** — зарегистрированный плагин генерации кода, хранящийся в таблице `plugins`
- **Tag** — строковая метка, присвоенная плагину для категоризации (например, `go`, `grpc`, `official`)
- **Tags** — массив строк (тегов), ассоциированный с конкретным плагином
- **Registry** — адаптер, обеспечивающий доступ к данным плагинов в PostgreSQL
- **PluginInfo** — protobuf-сообщение и доменная структура, описывающая информацию о плагине
- **PluginFilter** — структура фильтрации при запросе списка плагинов
- **SDK_Client** — Go-клиент для взаимодействия с EasyP API Service

## Требования

### Требование 1: Хранение тегов в базе данных

**User Story:** Как администратор платформы, я хочу хранить теги для каждого плагина в базе данных, чтобы плагины можно было категоризировать.

#### Критерии приёмки

1. THE Plugin_Tags_Service SHALL хранить теги каждого плагина в виде массива строк в колонке `tags` типа `text[]` таблицы `plugins` со значением по умолчанию `'{}'`
2. WHEN новый плагин добавляется без указания тегов, THE Plugin_Tags_Service SHALL присвоить пустой массив в качестве значения колонки `tags`
3. THE Plugin_Tags_Service SHALL применить изменение схемы через новый файл миграции в директории `migrate/`

### Требование 2: Теги в proto-определении

**User Story:** Как разработчик, использующий API, я хочу получать теги плагина в ответе gRPC, чтобы видеть категории каждого плагина.

#### Критерии приёмки

1. THE Plugin_Tags_Service SHALL включать поле `repeated string tags` в сообщение `PluginInfo` в файле `api/generator/v1/generator.proto`
2. WHEN плагин не имеет тегов, THE Plugin_Tags_Service SHALL возвращать пустой список в поле `tags` сообщения `PluginInfo`

### Требование 3: Теги в доменной модели

**User Story:** Как разработчик сервиса, я хочу иметь поле тегов в доменных типах, чтобы передавать теги между слоями приложения.

#### Критерии приёмки

1. THE Plugin_Tags_Service SHALL включать поле `Tags` типа `[]string` в структуру `PluginInfo` в файле `internal/core/domain.go`
2. THE Plugin_Tags_Service SHALL включать поле `Tags` типа `[]string` в структуру `PluginFilter` в файле `internal/core/domain.go`

### Требование 4: Чтение и запись тегов в адаптере реестра

**User Story:** Как разработчик сервиса, я хочу чтобы адаптер реестра корректно читал и записывал теги из/в базу данных, чтобы данные тегов были доступны на всех уровнях.

#### Критерии приёмки

1. WHEN Registry выполняет запрос `List`, THE Registry SHALL включать колонку `tags` в SQL-запрос и заполнять поле `Tags` в каждом возвращаемом `PluginInfo`
2. WHEN Registry выполняет запрос `Get`, THE Registry SHALL включать колонку `tags` в SQL-запрос и заполнять поле `Tags` в информации о плагине
3. WHEN PluginFilter содержит непустое поле `Tags`, THE Registry SHALL фильтровать плагины, возвращая только те, которые содержат все указанные теги (оператор `@>` для массивов PostgreSQL)

### Требование 5: Передача тегов через API-слой

**User Story:** Как пользователь API, я хочу видеть теги в ответе метода `Plugins`, чтобы использовать их для категоризации плагинов.

#### Критерии приёмки

1. WHEN API-слой формирует ответ `PluginsResponse`, THE Plugin_Tags_Service SHALL маппить поле `Tags` из доменного `PluginInfo` в поле `tags` protobuf-сообщения `PluginInfo`

### Требование 6: Фильтрация по тегам в SDK

**User Story:** Как разработчик, использующий SDK, я хочу фильтровать плагины по тегам, чтобы находить плагины нужной категории.

#### Критерии приёмки

1. THE SDK_Client SHALL включать поле `Tags` типа `[]string` в структуру `PluginFilter` в пакете `sdk`
2. WHEN PluginFilter содержит непустое поле `Tags`, THE SDK_Client SHALL фильтровать плагины, возвращая только те, у которых все указанные теги присутствуют в поле `tags`
3. WHEN PluginFilter содержит пустое поле `Tags`, THE SDK_Client SHALL не применять фильтрацию по тегам

### Требование 7: Обработка ошибок

**User Story:** Как пользователь системы, я хочу получать понятные ошибки при некорректных данных тегов, чтобы быстро исправлять проблемы.

#### Критерии приёмки

1. IF тег содержит пустую строку, THEN THE Plugin_Tags_Service SHALL игнорировать пустую строку при фильтрации
2. IF запрос к базе данных с фильтром по тегам завершается ошибкой, THEN THE Registry SHALL возвращать обёрнутую ошибку с контекстом операции
