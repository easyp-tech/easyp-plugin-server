# Перенос аудита в бизнес-логику — Requirements

**Status:** Draft
**Author:** AI agent
**Date:** 2026-04-14

## Обзор

Аудит-логирование переносится из gRPC interceptor'а (`AuditInterceptor`) в core-методы бизнес-логики. Каждый метод `core.Core` будет самостоятельно формировать `AuditEntry` с полным бизнес-контекстом и отправлять её в канал с blocking-семантикой. Это обеспечивает гарантированную доставку аудит-событий, покрытие всех транспортов (gRPC, MCP) и возможность легко расширять набор метаданных.

## Глоссарий

| Термин | Определение | Code Artifact |
|--------|------------|---------------|
| AuditEntry | Доменная структура одной аудит-записи | `internal/core/domain.go` → `AuditEntry` |
| AuditSender | Механизм отправки аудит-записей из core (blocking send в канал) | `internal/core/core.go` |
| Caller IP | IP-адрес вызывающего клиента, прокинутый через context на transport layer | `peer.FromContext` / `realip` middleware |

## User Stories

- Как **оператор системы**, я хочу чтобы аудит-записи содержали полный бизнес-контекст (plugin info, file count и т.д.), чтобы при расследовании инцидентов не приходилось сопоставлять данные из нескольких источников.
- Как **оператор системы**, я хочу гарантию что ни одно аудит-событие не потеряется, чтобы аудит-лог был полным и достоверным.
- Как **разработчик**, я хочу легко расширять набор метаданных аудит-записи, чтобы при добавлении новой бизнес-информации не приходилось менять схему или архитектуру.

## Требования

### Группа 1: Перенос аудита в core

**REQ-1.1** WHEN любой из пяти бизнес-методов (`Generate`, `ListPlugins`, `CreatePlugin`, `UpdatePlugin`, `DeletePlugin`) завершается успешно, the system SHALL сформировать `AuditEntry` с полными бизнес-данными и отправить её в аудит-канал.

**REQ-1.2** WHEN любой из пяти бизнес-методов завершается с ошибкой, the system SHALL сформировать `AuditEntry` со статусом error, кодом и сообщением ошибки и отправить её в аудит-канал.

**REQ-1.3** WHEN `AuditEntry` формируется в core-методе, the system SHALL заполнить поля `OperationType`, `PluginName`, `CallerAddress`, `Status`, `ErrorCode`, `ErrorMessage`, `DurationMs`, `Metadata` и `CreatedAt`.

**REQ-1.4** WHEN core-метод формирует `AuditEntry`, the system SHALL извлечь `CallerAddress` из context (прокинутый transport layer).

### Группа 2: Гарантированная доставка

**REQ-2.1** WHEN core-метод отправляет `AuditEntry` в канал и канал полон, the system SHALL блокироваться до тех пор, пока в канале не освободится место или context не будет отменён.

**REQ-2.2** WHEN context отменяется во время ожидания свободного места в канале, the system SHALL прекратить ожидание и не терять бизнес-ответ (ошибку или результат вернуть вызывающему коду).

### Группа 3: Расширяемость метаданных

**REQ-3.1** WHEN core-метод формирует `AuditEntry`, the system SHALL записывать бизнес-специфичные данные в поле `Metadata` типа `map[string]any`.

**REQ-3.2** WHEN в будущем потребуется добавить новые метаданные, the system SHALL поддерживать добавление новых ключей в `Metadata` без изменения схемы БД или интерфейса `AuditLog`.

### Группа 4: Удаление interceptor'а

**REQ-4.1** WHEN gRPC-запрос проходит через middleware chain, the system SHALL не содержать `AuditInterceptor` в цепочке interceptor'ов.

**REQ-4.2** WHEN MCP-запрос вызывает бизнес-метод через `CoreService`, the system SHALL аудитировать вызов на том же уровне, что и gRPC-запрос (в core).

### Группа 5: Сохранение существующего поведения

**REQ-5.1** WHEN аудит-запись отправлена в канал, the system SHALL обработать её существующим `Worker` и сохранить через `Store` в таблицу `audit_log` без изменения Worker и Store.

**REQ-5.2** WHEN сервис завершает работу (shutdown), the system SHALL дождаться обработки оставшихся аудит-записей в канале с таймаутом (существующая логика `Worker.Shutdown`).

## Топологический порядок

REQ-1.4 → REQ-1.1, REQ-1.2, REQ-1.3
Причина: извлечение caller IP из context (1.4) должно работать до формирования AuditEntry (1.1–1.3).

REQ-4.1 → REQ-1.1
Причина: interceptor удаляется (4.1) одновременно с добавлением аудита в core (1.1), чтобы не дублировать записи.

REQ-2.1 (зависит от REQ-1.1 — blocking send реализуется в рамках отправки из core)

REQ-3.1 (параллельно — касается формата, не порядка)
REQ-5.1, REQ-5.2 (параллельно — существующее поведение, без изменений)
