# Переход на goose — Требования

**Status:** Draft
**Author:** agent
**Date:** 2026-05-26

## Обзор

Замена самописной системы миграций (`internal/database/migrations/`) на библиотеку [pressly/goose](https://github.com/pressly/goose). Миграции вкомпилируются в бинарник через `embed.FS`, применяются автоматически при старте сервиса с advisory lock. Существующие 5 SQL-миграций конвертируются в goose-формат. Самописный миграционный код (~450 строк) удаляется.

## Глоссарий

| Термин | Определение | Code Artifact |
|--------|------------|---------------|
| goose | Библиотека миграций для Go с поддержкой SQL/Go миграций, embed.FS, advisory locking | `github.com/pressly/goose/v3` |
| `embed.FS` | Стандартный Go-механизм встраивания файлов в бинарник на этапе компиляции | `embed` (stdlib) |
| Advisory lock | PostgreSQL-механизм блокировки, предотвращающий одновременное выполнение миграций несколькими инстансами | `goose.NewPostgresSessionLocker` |

## Требования

### Группа 1: Встраивание миграций

**REQ-1.1** WHEN сервис собирается (`go build`), the system SHALL включить все SQL-файлы миграций из директории `migrate/` в итоговый бинарник через `embed.FS`.

**REQ-1.2** WHEN параметр конфигурации `DB.MigrateDir` больше не используется, the system SHALL удалить его из структуры `dbConfig` и всех связанных конфигурационных файлов.

### Группа 2: Применение миграций при старте

**REQ-2.1** WHEN сервис запускается, the system SHALL применить все pending миграции через goose до открытия основного connection pool (до `database.NewSQL`).

**REQ-2.2** WHEN все миграции уже применены, the system SHALL продолжить запуск без ошибок.

**REQ-2.3** WHEN миграция завершается с ошибкой, the system SHALL прервать запуск сервиса и вернуть ошибку с указанием номера и имени проблемной миграции.

**REQ-2.4** WHEN несколько инстансов сервиса запускаются одновременно, the system SHALL использовать PostgreSQL advisory lock для предотвращения параллельного выполнения миграций.

### Группа 3: Формат миграций

**REQ-3.1** WHEN создаётся новая миграция, the system SHALL использовать формат файлов goose: `NNNNN_name.sql` с маркерами `-- +goose Up` / `-- +goose Down`.

**REQ-3.2** WHEN goose выполняет миграцию, the system SHALL оборачивать каждую миграцию в транзакцию (поведение goose по умолчанию).

### Группа 4: Удаление старого кода

**REQ-4.1** WHEN переход завершён, the system SHALL не содержать пакет `internal/database/migrations/` и все его файлы.

**REQ-4.2** WHEN переход завершён, the system SHALL не содержать импорт `internal/database/migrations` ни в одном файле проекта.

### Группа 5: Состояние миграций

**REQ-5.1** WHEN goose применяет миграции, the system SHALL использовать таблицу `goose_db_version` для отслеживания состояния (стандартная таблица goose).

**REQ-5.2** WHEN среда создаётся с нуля, the system SHALL не требовать наличия старой таблицы `migration` — переноса state не требуется.

## Топологический порядок

```
REQ-1.1 → REQ-1.2 → REQ-2.1 → REQ-2.2, REQ-2.3, REQ-2.4
REQ-3.1, REQ-3.2 (параллельно с группой 2)
REQ-4.1, REQ-4.2 (после всех остальных)
REQ-5.1, REQ-5.2 (параллельно с группой 2)
```

Причина: сначала нужно встроить миграции (1.1), затем обновить вызов (2.1), потом убедиться в корректности happy/error path (2.2, 2.3, 2.4), и в конце удалить старый код (4.x).
