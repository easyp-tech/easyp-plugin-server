# Требования: plugin-migration-cli

**Статус:** Draft
**Автор:** Antigravity
**Дата:** 2026-06-21

## Обзор
Необходимо реализовать команду `easyp-svc plugins migrate <path>`, которая сканирует указанную директорию на наличие собранных бинарников плагинов и регистрирует их в EasyP Service через gRPC API. Команда должна предоставлять информативный динамический интерфейс (Mini-TUI) при запуске в интерактивном режиме и поддерживать простой вывод логов для автоматизированных сред (CI/CD).

## Глоссарий

| Термин | Определение | Артефакт кода |
|------|------------|---------------|
| `Migrator` | Компонент CLI, выполняющий сканирование файловой системы и регистрацию плагинов | `cmd/easyp-svc/` |
| `EasyP Service` | gRPC-сервер, обслуживающий запросы регистрации и генерации кода | `internal/serve/` |
| `AlreadyExists` | Стандартный статус ошибки gRPC (`codes.AlreadyExists`), возвращаемый сервером, если плагин с такими группой, именем и версией уже зарегистрирован | `internal/api/` |

## Пользовательские сценарии

- Как **системный администратор**, я хочу иметь возможность зарегистрировать все собранные плагины одной командой, чтобы они стали доступны пользователям без ручного внесения каждого плагина.
- Как **разработчик**, я хочу видеть понятный прогресс-бар и спиннеры выполнения во время миграции, чтобы понимать, на каком этапе находится процесс и сколько плагинов уже обработано.
- Как **инженер CI/CD**, я хочу запускать мигратор в неинтерактивном режиме (например, в пайплайнах развертывания), чтобы получать чистые последовательные логи выполнения в stdout без управляющих символов терминала.

## Требования

### 1. Сканирование файловой системы
**REQ-1.1** WHEN команда `plugins migrate` вызывается без обязательного позиционного аргумента `<path>`, the system SHALL вывести ошибку валидации аргументов и инструкцию по использованию в stderr, после чего завершиться с кодом 1.

**REQ-1.2** WHEN команда вызывается с корректным аргументом `<path>`, the system SHALL рекурсивно обойти указанную директорию и найти все исполняемые файлы с именем `plugin`, расположенные по путям, соответствующим структуре `{group}/{name}/{version}/plugin`.

**REQ-1.3** WHEN директория или файл не соответствуют структуре путей `{group}/{name}/{version}/plugin`, the system SHALL проигнорировать их при формировании списка миграции.

### 2. Регистрация плагинов через gRPC
**REQ-2.1** WHEN для найденного плагина формируется конфигурация, the system SHALL составить `CreatePluginRequest` с полями `Group`, `Name`, `Version`, а также объектом `Config`, содержащим массив `command` с единственным элементом `pluginsPrefix + "/" + group + "/" + name + "/" + version + "/plugin"`.

**REQ-2.2** WHEN флаг `--plugins-prefix` не задан явно, the system SHALL использовать значение по умолчанию `/plugins`.

**REQ-2.3** WHEN отправляется запрос регистрации, the system SHALL выполнить gRPC-вызов `CreatePlugin` к серверу по адресу, указанному во флаге `--addr` (значение по умолчанию `localhost:8080`).

### 3. Обработка ответов сервера
**REQ-3.1** WHEN сервер возвращает успешный ответ (плагин создан), the system SHALL увеличить счетчик успешно зарегистрированных плагинов и отобразить успех в UI.

**REQ-3.2** WHEN сервер возвращает ошибку со статусом `codes.AlreadyExists`, the system SHALL пропустить данный плагин без аварийного завершения, увеличить счетчик пропущенных плагинов и отобразить этот статус в UI.

**REQ-3.3** WHEN сервер возвращает любую другую ошибку, the system SHALL зафиксировать ошибку в статистике, увеличить счетчик ошибок и продолжить регистрацию остальных плагинов.

### 4. Фильтрация плагинов
**REQ-4.1** WHEN задан флаг `--filter`, the system SHALL отфильтровать найденные плагины и отправлять запросы регистрации только для тех плагинов, чьи `{group}/{name}` или `{group}/{name}:{version}` соответствуют указанному glob-шаблону (например, `connectrpc/*`).

### 5. Интерфейс пользователя (UI/UX)
**REQ-5.1** WHEN команда запущена в интерактивном терминале (TTY) и флаг `--non-interactive` не передан, the system SHALL отображать динамический интерактивный Mini-TUI: текущий шаг, спиннер обработки активного плагина, прогресс-бар вида `[████░░░] 45%` и счетчик прогресса `(X/Y)`.

**REQ-5.2** WHEN команда запущена в неинтерактивном окружении (non-TTY) или передан флаг `--non-interactive`, the system SHALL отключать динамическое обновление строк и выводить плоский лог в stdout для каждой операции (успех, пропуск, ошибка).

**REQ-5.3** WHEN процесс миграции завершается, the system SHALL вывести итоговую таблицу со сводной статистикой (всего плагинов, успешно зарегистрировано, пропущено, завершилось ошибкой) и вернуть код выхода 0, если критических сбоев при запуске не произошло.

## Топологический порядок выполнения

```
REQ-1.1 → REQ-1.2 → REQ-1.3  (Сканирование и фильтрация файлов плагинов)
   ↓
REQ-2.1 → REQ-2.2 → REQ-2.3  (Формирование и отправка gRPC запросов)
   ↓
REQ-3.1 → REQ-3.2 → REQ-3.3  (Обработка результатов)
   ↓
REQ-4.1                      (Применение glob-фильтра)
   ↓
REQ-5.1 → REQ-5.2 → REQ-5.3  (Интерактивный/неинтерактивный UI/UX)
```
*Обоснование:* Сканирование директории должно быть реализовано до отправки запросов. Обработка результатов gRPC-вызовов зависит от отправки запросов, а отображение прогресса и итоговой таблицы зависит от получения результатов обработки.
