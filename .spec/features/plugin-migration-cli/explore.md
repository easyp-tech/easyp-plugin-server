# Exploration: plugin-migration-cli

## Intent
Необходимо разработать команду миграции плагинов `easyp-svc plugins migrate <path>` (где `<path>` — обязательный позиционный аргумент пути сканирования). Команда сканирует директорию с собранными плагинами, находит бинарники плагинов, соответствующих структуре `{group}/{name}/{version}/plugin`, и регистрирует их в EasyP Service через gRPC API.
Ключевые требования:
1. Информативный и удобный UI/UX, отображающий процесс миграции: какие плагины устанавливаются, текущие шаги, прогресс выполнения (сколько установлено/всего), а также финальный отчет.
2. Возможность ограничения устанавливаемых плагинов через фильтрацию по путям (позиционный аргумент) и по шаблонам через флаг `--filter`.
3. Корректная обработка уже существующих плагинов (пропуск с уведомлением пользователя).

## Investigation
В ходе исследования кодовой базы было установлено:
1. **CLI Каркас**: В `cmd/easyp-svc/main.go` настроена структура команд на базе `urfave/cli/v3`. Имеется заготовка команды:
   ```go
   {
       Name:  "plugins",
       Usage: "Manage plugins",
       Commands: []*cli.Command{
           {
               Name:  "migrate",
               Usage: "Run migrations for plugins",
               Action: func(ctx context.Context, cmd *cli.Command) error {
                   ...
               },
           },
       },
   }
   ```
2. **gRPC Клиент**: В `sdk/client.go` уже реализованы методы `CreatePlugin` и `ListPlugins` для взаимодействия с API EasyP. `CreatePlugin` принимает `group`, `name`, `version`, `pluginConfig map[string]any` и `tags []string`. Мы можем переиспользовать `sdk.Client` для регистрации плагинов.
3. **Структура плагинов**: Конфигурация плагина в БД содержит поле `config` (json), в котором указывается путь к исполняемому файлу плагина на стороне сервера в формате:
   `{"command": ["/plugins/{group}/{name}/{version}/plugin"]}`
   Путь `/plugins` является префиксом на стороне сервера. При регистрации путь формируется как:
   `pluginsPrefix + "/" + group + "/" + name + "/" + version + "/plugin"`

## Options Considered

### Option A: Полноэкранный TUI на базе `github.com/charmbracelet/bubbletea`
Интерактивный полноэкранный интерфейс с панелями логов, списком плагинов и красивым прогресс-баром.
- **Pros**: Очень красивый интерфейс, возможность интерактивной навигации по списку ошибок и результатов.
- **Cons**: Требует добавления тяжелых внешних зависимостей (`bubbletea`, `lipgloss` и др.), усложняет код CLI, увеличивает размер бинарника. Для простой утилиты миграции полноэкранное приложение является избыточным.
- **Complexity**: Высокая

### Option B: Интерактивный CLI на базе ANSI-последовательностей (Mini-TUI) с автодетектом TTY
Компактный динамический интерфейс прямо в потоке вывода. Использует `\r` (carriage return) для перезаписи строк, отображает анимированные спиннеры выполнения и текстовый прогресс-бар. При отсутствии TTY (или при наличии флага `--non-interactive`) автоматически переключается на простой последовательный вывод логов.
- **Pros**: Отсутствие внешних зависимостей (чистый Go с пакетами `fmt`, `os`), легкий вес бинарника, сохраняет историю прокрутки терминала, прост в поддержке, отлично подходит для CI/CD.
- **Cons**: Менее гибкий визуально по сравнению с полноэкранным TUI.
- **Complexity**: Средняя / Низкая

## Constraints & Risks
- **Обработка ошибок gRPC**: При попытке зарегистрировать уже существующий плагин сервер возвращает ошибку `codes.AlreadyExists`. Этот случай должен корректно перехватываться клиентом, учитываться в статистике как "пропущенный" (skipped) и отображаться в UI без аварийного завершения программы.
- **Безопасность путей**: Поскольку сканируется переданный пользователем путь, необходимо исключить возможность directory traversal и корректно валидировать структуру папок `{group}/{name}/{version}/plugin`.
- **Интерактивность в CI/CD**: В средах автоматизации (CI/CD) интерактивный режим (перезапись строк через `\r`) поломает вывод логов. Автоматическое определение TTY через `golang.org/x/sys/unix` (или проверку дескриптора) является критически важным.

## Recommended Direction
Рекомендуется использовать **Option B (Интерактивный CLI / Mini-TUI)**. Он обеспечивает отличный UX (показывает текущие шаги, прогресс-бар, спиннеры и понятную финальную статистику), не требует затягивания тяжелых зависимостей и сохраняет максимальную совместимость с CI/CD-системами.

## Scope Boundaries

### Must-have (v1)
- CLI-команда `easyp-svc plugins migrate <path>` (с обязательным позиционным аргументом `<path>`).
- Флаги:
  - `--addr` — адрес gRPC-сервера (по умолчанию `localhost:8080`).
  - `--filter` — шаблон фильтрации плагинов (например, `connectrpc/*`).
  - `--non-interactive` — форсированное отключение интерактивного UI.
  - `--plugins-prefix` — префикс директории плагинов на сервере (по умолчанию `/plugins`).
- Автоматическое определение TTY для переключения между интерактивным Mini-TUI и обычным лог-выводом.
- Сканирование указанного пути на наличие структуры `{group}/{name}/{version}/plugin`.
- Фильтрация найденных плагинов как по позиционному пути, так и по шаблону `--filter`.
- Отображение интерактивного прогресса: активный спиннер, имя обрабатываемого плагина, прогресс-бар `[████░░░] 45%`.
- Логирование результатов: пропущенные (со статусом `AlreadyExists`), успешно зарегистрированные и ошибки.
- Итоговый резюмирующий отчет.

### Deferred (v2)
- Флаг `--force` для обновления конфигурации плагина, если он уже зарегистрирован в базе данных.
- Параллельное выполнение gRPC-запросов для ускорения миграции.
